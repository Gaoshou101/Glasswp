# 液态玻璃与卡片动效可行性报告

日期：2026-10-13，Asia/Shanghai。对象：本项目 Wallpaper Engine Web 壁纸。

本次完成源码检查、既有画面检查、官方资料核对和本机进程占用短时采样。**界面、桥接、桌面壁纸和宿主配置均未修改。下文的新增占用是工程预测，不是新效果的实测成绩。**

## 1. 结论

**可以做成苹果 Liquid Glass 风格，也可以给各功能卡片加入交互和动态反馈。建议默认采用“轻量液态”，将真实局部折射作为可选增强项。**

现有 TypeScript、CSS 和 Wallpaper Engine Web 技术栈可以继续使用。第一阶段无需引入 React、重型动画框架或修改 .NET 数据桥接。

| 方案 | 可获得的效果 | 可行性与建议 |
| --- | --- | --- |
| A：轻量液态，默认推荐 | 更清透的材质、立体边缘、随鼠标移动的光泽、轻微弹性、按压反馈、平滑翻页 | 可行性高；主要使用 CSS 与少量事件驱动 JavaScript；成本最容易控制 |
| B：局部真实折射，可选 | 在 A 基础上，让背景在卡片边缘呈现透镜弯曲；交互时产生短暂折射变化 | 可行性中高；SVG 位移或小型 WebGL 渲染需在实际 WE 宿主验证 |
| C：持续实时折射，实验选项 | 每张卡片持续改变折射、波动和环境光，接近复杂液态材质演示 | 技术上可做；高分辨率下持续消耗 GPU，开发与维护成本最高；不建议作为常驻默认效果 |

苹果原生效果由其平台组件提供，Windows Web 壁纸需要自行实现视觉与交互近似。A 不包含真实光学折射；B/C 也不能承诺与苹果原生渲染完全一致。[Apple 技术概览](https://developer.apple.com/documentation/technologyoverviews/liquid-glass)

### 2.2 加动画前要解决的三个问题

1. **额度卡片节点被反复重建。** `QuotaComponent.update()` 每次调用 `render()`，后者清空内容再创建卡片及分页按钮。当前约每两秒发生一次。若直接附加进入动画、悬停状态或事件，会出现重复入场、焦点丢失和交互中断。应按账号/窗口标识保留节点，普通刷新只更新变动字段；真实翻页才播放切换动画。
2. **已有布局变换不能被悬停动效覆盖。** `applyAppearance()` 用 `transform` 设置区域位置和大小。液态反馈应放在内层材质/内容层，位置缩放与动效分别负责各自层级。
3. **进度条和趋势图更新方式需要收敛。** 进度条目前使用 `width`；硬件趋势 SVG 每次更新被删除重建。建议分别改成固定宽度配合 `scaleX`、保留 SVG 并更新折线。数值没变化时不反复写入，也不播放动画。

## 3. 建议的视觉与交互方案

### 3.1 材质方向

保留上下区域、淡紫强调和人物面部留白。将玻璃调整为有厚度的透明面板，光泽集中在边缘及交互位置，数字保持稳定清晰。

| 设计项 | 建议 |
| --- | --- |
| 初始材质范围 | 透明度 82–90%、模糊 18–28 个设计单位、边缘高光 60–75%；作为试调范围，亮色头发背景处可增加底色遮蔽 |
| 色彩 | 主文字 `#F6F3FF`、次文字 `#D9D0E5`、紫色强调 `#D4B4FF`、玻璃底色 `#14111C`、警示 `#E9B7B8`；实际对比度由透明混合后的背景决定 |
| 字体 | 延续 Segoe UI / 微软雅黑 UI；数字保持等宽宽度，避免更新时跳动 |
| 厚度感 | 内外两道柔和边缘、局部高光、克制阴影；A 用视觉模拟，B 增加背景边缘真实位移 |
| 文字层 | 与材质层分开；文字本身不模糊、不折射、不随透明度一起变淡 |
| 内部账号卡片 | 使用薄的半透明填色和焦点反馈，不再叠背景滤镜 |
| 静止状态 | 默认没有持续波纹、闪烁和大幅漂浮；鼠标进入或功能状态变化时才产生动态反馈 |

Apple 将 Liquid Glass 的透镜感、光泽反馈和柔性运动视为一个整体，并建议保持层级、避免玻璃层反复叠加。本项目据此采用外壳材质与内部内容分层的设计。[Meet Liquid Glass](https://developer.apple.com/videos/play/wwdc2025/219/)

### 3.2 各功能卡片可以增加的效果

| 对象 | 交互/动态建议 | 触发与限制 |
| --- | --- | --- |
| 时钟 | 悬停边缘光泽、轻微抬升；时间变化可做短暂过渡 | 不每秒播放整张卡片入场；默认保持数字直接可读 |
| 天气 | 图标在天气类型改变时短暂过渡；点击展开已有天气信息 | 只展示当前数据契约已有的城市、最高/最低温及时间等，不凭空添加小时预报 |
| 额度外壳 | 翻页时轻微横向位移配合淡入淡出；按钮有按压回弹 | 约 220–320 ms；悬停、聚焦或详情打开时暂停自动轮播 |
| 内部账号卡片 | 悬停局部光泽、焦点边缘；点击/聚焦展示完整窗口和绝对重置时间 | 保留未知、参考、过期、等待更新等原有语义；动画不模拟余额恢复 |
| 刷新按钮 | 按压反馈、请求期间图标旋转、成功/失败反馈 | 沿用现有真实任务状态；仅请求期间持续动画，继续禁止重复提交 |
| CPU/GPU | 悬停光泽与抬升；点击展开已有设备名、温度、趋势 | 数值更新可短暂交叉淡入；不由 GPU 利用率驱动更强波纹，避免资源反馈循环 |
| 显存/RAM | 同样的材质反馈；点击展开使用量/容量及趋势 | 保留真实采样值；首次阶段不新增监控传感器 |
| 所有操作按钮 | 轻微按压缩放、释放回弹、清晰焦点 | 所有光泽装饰层 `pointer-events:none`，保留按钮命中区域 |

建议抬升 1–3 个设计像素、倾斜不超过约 1°、按压缩放约 0.98–0.99。详情用已有边界内的浮层或可关闭面板，并约束到安全区，避免覆盖角色面部及底部任务栏。

实际桌面鼠标事件需要在 WE 中验证，桌面图标与宿主输入设置可能影响命中。浏览器预览可实现焦点/键盘交互；桌面关键功能仍需有 WE 属性或管理页入口，避免依赖壁纸获得键盘焦点。

## 4. 实现路线与性能控制

### A：轻量液态

- 继续使用现有背景模糊，半径在交互期间固定。高光优先做成预绘制渐变纹理，通过 `transform` 和 `opacity` 移动/显隐。
- 鼠标事件只保存最新坐标；一个共享调度器按帧读取一次。进入活动状态才启动，弹性收敛后停止。
- 缓存卡片边界，在尺寸/位置变化时更新；避免每帧读布局再写样式。
- 图标和按钮优先使用有限时长动画；请求状态结束后停转。仅对正在运动的必要元素使用 `will-change`，完成后撤销。
- 即使只改 `transform`，含背景滤镜的元素也可能发生额外采样或重绘，因此仍要在 CEF 中检查合成与绘制成本。[MDN 动画性能说明](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/CSS_JavaScript_animation_performance)

### B：局部真实折射

- 优先验证 SVG 位移滤镜与背景滤镜的组合是否在实际 CEF 中正确显示。CSS 能解析该值，不足以证明折射被正确渲染。
- 可替代实现：共用一个小型 WebGL 渲染器，采样本地背景图，用圆角距离场和法线生成边缘透镜感；文字继续用 DOM。
- 当前背景静态，可在布局/材质改变时计算并缓存静止折射；悬停期间才改变局部参数。校准 `object-fit:cover` 裁切、屏幕缩放和设备像素比。
- 限制折射到卡片边缘；不要给每个嵌套窗口创建独立 WebGL 上下文。

### C：持续实时折射

需要连续运行着色器、多个中间纹理或更复杂的材质遮罩；动态背景、多个屏幕与复杂卡片形变会进一步增加成本。可用于展示模式，但常驻默认应保留 A/B 的按需运行方式。

### 共用策略

1. 数据继续按现有频率采集；动画不增加上游请求或硬件采样频率。
2. JavaScript/着色器活动更新采用 `requestAnimationFrame`，按宿主 FPS 和所选质量上限限制实际更新次数，默认质量上限建议 30 FPS。宿主上限更低时遵循宿主值。[WE FPS 官方说明](https://docs.wallpaperengine.io/en/web/performance/fps.html)
3. 宿主暂停、页面隐藏、动态关闭时，取消视觉调度、停止相关动画和请求；恢复时重置动画时间基准、读取新快照，避免补算停顿期间的帧。WE 当前文档说明渲染进程会冻结，显式生命周期处理仍有助于统一预览和恢复行为。[WE 属性/暂停接口](https://docs.wallpaperengine.io/en/web/api/propertylistener.html)
4. `prefers-reduced-motion` 下保留清透材质和必要状态反馈，关闭倾斜、回弹、旋转及连续运动。
5. 新增“材质模式”和“动态强度”选项；旧的透明度、模糊、高光继续可用。Studio 与 WE 属性分开保存的现状要保持明确。

### 5.2 新效果增量预测

以下是假设 **单个 1600×2560 像素画布、30 FPS 活动上限、7 个外层玻璃区域、静态背景、无长期打开的额外详情层** 时，针对本机硬件的规划区间。A/B 的闲置列假设停止新增的运动调度；底层数据和原有柔光可继续工作。

**置信度：内存/显存量级为中等；CPU/GPU 百分点为低，待原型 A/B 校准。它们是设计预算预测，没有通用公式能仅凭 CSS 精确得出利用率。**

| 档位/状态 | 整机 CPU 增量 | GPU 3D 引擎利用率增量 | 私有内存提交量增量 | 专用显存增量 |
| --- | --- | --- | --- | --- |
| A 轻量液态，闲置 | +0–0.3 个百分点 | +0–1 个百分点 | +20–60 MiB | +16–48 MiB |
| A 轻量液态，持续交互/切换期间 | +0.2–0.8 个百分点 | +1–3 个百分点 | 同上，瞬时缓存可能额外增长 | 同上 |
| B 局部折射，静止结果缓存 | +0–0.4 个百分点 | +0–2 个百分点 | +50–120 MiB | +48–128 MiB |
| B 局部折射，活动期间 | +0.4–1.5 个百分点 | +3–7 个百分点 | 同上，首次生成纹理可能有峰值 | 同上 |
| C 持续实时折射，持续活动 | +1–3 个百分点 | +6–15 个百分点 | +100–250 MiB | +96–256 MiB |

表中的“百分点”是绝对差值：例如 CPU 0.55% 增加 0.3 个百分点后是 0.85%。GPU 列是对应 3D 引擎计数的预测差值，**不是**整张显卡的算力消耗或功耗百分比。

若 A 有约 20% 的时间处于活动交互，按上述区间加权，其长期平均新增约为 CPU **0.04–0.40 个百分点**、GPU 3D 计数 **0.2–1.4 个百分点**。这个 20% 是计算示例，不是对用户使用习惯的测量。

因此，本机默认使用 A 的新增成本预期较小；B 的内存容量需求也较容易容纳，但活动功耗需要实测；C 的主要代价是持续 GPU 活动及潜在频率提升，而非内存容量不足。

### 5.3 内存估算依据

- 1600×2560 的一张 RGBA8 全屏缓冲约 **15.6 MiB**。
- 默认玻璃矩形合计约 158.5 万像素，同格式的一套局部缓冲约 **6.0 MiB**。
- 原始 2160×3840 背景解码为 RGBA8 约 **31.6 MiB**。这属于已有背景成本；仅在复制为额外 CPU/GPU 资源时计入新增成本，不能重复算作每档必增。
- A 以少量高光/合成缓存为主；B 增加位移、法线、背景采样或中间纹理；C 可能增加多次渲染缓存。纹理精度、滤镜外扩、全屏中间层、对齐和驱动缓存会放大理论值。
- WebGL GPU 纹理、CPU 副本与浏览器私有内存可能由不同计数体现，不能把这些理论缓冲机械地加到所有指标上。

### 5.4 分辨率、帧率与多屏

| 变化 | 预计影响 |
| --- | --- |
| 800×1280 相对 1600×2560 | 像素面积为 1/4；相关纹理和像素处理成本下降，浏览器固定开销和事件处理不会变成 1/4 |
| 2160×3840 相对 1600×2560 | 像素面积约 2.03 倍；局部纹理显存可近似按面积放大，GPU 利用率不保证线性增长 |
| 活动 30 FPS 提高到 60 FPS | 活动绘制次数翻倍；GPU 动态部分可先按约 1.5–2 倍预算，固定开销和缓存容量通常不会翻倍 |
| 折射渲染尺寸设为 0.75 倍 | 对应像素面积约 56%；影响玻璃内部采样质量，DOM 文字仍保持原分辨率 |

| 宿主暂停 | 新动画调度停止后，新增绘制成本应接近零；保留的纹理内存通常不会立即释放 |

本次未测电力、GPU 频率、帧时间或游戏性能，不能给出可靠的瓦数、温度变化或 FPS 损失承诺。

## 6. 后续实施与验收建议

### 6.1 推荐顺序

1. **建立真正的 A/B 基准。** 固定目标显示器、实际像素尺寸、背景、属性、30 FPS、数据内容及运行窗口；记录现有版本。
2. **先稳定组件更新。** 额度节点保留、趋势更新复用、布局/材质层分离；避免动画每次轮询重新触发。
3. **实现 A 原型。** 先验证一大一小两种卡片的高光与按压，再扩展到其他区域；加入真实翻页和刷新反馈。
4. **实际 WE 验证并校准预算。** 达到成本目标后，再验证 B 的折射视觉与收益；C 保留为明确可选的展示模式。

范围估算：A 完整实现及宿主回归约 **2–4 个开发工作日**；B 另加约 **2–4 日**；C 另加约 **5–10 日或更多**。这是任务量规划，受视觉迭代、宿主兼容性与验收范围影响，不是交付承诺。

### 6.2 性能验收口径

原版与候选版各预热 60 秒，同条件重复至少 3 轮，每轮闲置 3–5 分钟；另录制固定的 60 秒悬停、翻页、展开和关闭操作。桌面只运行一个目标壁纸画布，关闭额外预览，并记录其他工作负载和 GPU 电源状态。

| 验收项 | A 的初始目标 |
| --- | --- |
| 闲置平均新增 CPU | ≤0.3 个百分点 |
| 闲置平均新增 GPU 3D 计数 | ≤1 个百分点；同频率/电源状态比较，并同时观察时钟和功耗 |
| 固定交互期间平均新增 CPU/GPU | 分别 ≤0.8 / 3 个百分点 |
| 新增私有提交量/专用显存 | 分别 ≤60 / 48 MiB；预热后连续翻页不应持续增长 |
| 活动帧时间 | 30 FPS 下 P95 不超过约 33.3 ms；记录实际绘制/呈现，不只看 `requestAnimationFrame` 回调数 |
| 空闲与暂停 | 新视觉调度在回弹结束后停止；暂停期间不继续产生新增绘制任务 |
| 界面与数据正确性 | 快照不重复入场；刷新状态真实；未知/过期语义、分页顺序和配置保留 |

这些是拟定的验收目标，尚未验证。未达到目标时，依次降低活动区域数量、移除持续动画、减少中间纹理、降低折射分辨率，或回退 A；保留文字和真实数据质量。

功能回归还应覆盖 800×1280、1080×1920、1600×2560、2160×3840，以及常用显示缩放、桌面图标命中、已有按钮、宿主暂停/恢复、减少动态、断连、未知额度和人物安全区。

**最终建议：第一阶段落地 A，默认按需动态；第二阶段用实际 A/B 结果决定是否加入 B。** 这样能明显提升液态观感与交互，同时给常驻壁纸建立明确的资源预算。
