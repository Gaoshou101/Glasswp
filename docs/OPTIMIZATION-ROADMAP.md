## 3. A：先建立可靠基线与更新流程

### A1. 建立源码与产物版本

- 对准备纳入 Git 的源码、文档、预览素材做一次隐私与授权检查，再建立首个源码基线。私有目录、真实账号诊断、安装票据与运行产物继续留在忽略目录。
- 构建生成不含隐私信息的版本清单：构建 ID、时间、源码版本、前端资源摘要、桥接版本和数据契约版本。
- `/v1/health` 返回桥接构建 ID；宿主报告附带前端构建 ID，以识别“新桥接 + 旧页面”等组合。当前 `0.1.0` 与 `schemaVersion=1` 不足以区分历次安装。
- 尚无提交或工作区含未提交改动时，版本清单明确标记该状态，不能伪装成某个已提交版本。

### A2. 将构建、安装、启停分开

证据：`scripts/build.ps1` 发布后直接调用 `update-bridge.ps1`；后者停止桥接、复制文件，默认不启动，也没有完整版本备份或失败回退。

建议交付：

1. 构建命令默认只生成候选产物；独立更新命令负责安装。
2. 更新前记录运行状态、任务启动方式、权限和配置目录，备份旧发布文件并校验候选文件完整性。
3. 文件切换后按原运行方式恢复服务，等待健康检查与首个有效样本；失败恢复旧版本。
4. 明确报告“构建成功、安装成功、恢复运行、桌面验证”各自结果。

### A3. 固化壁纸安装时的属性保留

证据：`scripts/install-wallpaper.ps1` 备份旧 `project.json` 后用构建目录覆盖，随后只回填展示票据；未合并旧属性。`-Apply` 只有 `openWallpaper`，也未覆盖既有正式桌面同路径重载所需的 close/open 流程。目标固定为开发副本，无法直接表达当前正式使用的其他本地副本。

建议交付：显式目标目录与显示器、旧属性按名称迁移、新增属性补默认值、全量可回退备份、同路径先关闭再打开、构建 ID 与文件摘要核对。保留当前显示器选择、票据、材质、位置及额度开关。

**A 的验收条件**：正常更新与候选启动失败各演练一次；均保留配置，失败可恢复旧版本；更新记录能区分正式桌面与开发副本。新装、覆盖更新和回退均有可重复执行的检查。

## 4. B：隔离故障，避免一个问题扩大

下面是代码路径暴露的风险；本次没有通过破坏生产环境来复现崩溃或超时。

| 任务 | 当前证据 | 建议实现 | 验收 |
| --- | --- | --- | --- |
| B1：账号读取按账号隔离 | `RemoteSources.UpdateQuota()` 中逐账号 HTTP 非成功有回退，但网络异常/超时会进入循环外的 catch，结束本轮，后续账号不再继续 | 每账号设置请求预算、捕获该账号异常并保留其旧证据；继续读取其余账号，维持小规模有界执行 | 首个账号超时，其他账号仍完成更新；失败账号保留原观察时间并标过期 |
| B2：天气与额度调度解耦 | 后台先 `Task.WhenAll(upstream, weather)`，再读额度；天气慢响应会延后额度读取 | 各来源独立安排到期任务，同来源禁止重入；上游刷新成功后显式安排额度重读 | 天气超时不阻塞额度；手动/自动刷新仍合并，同一来源没有重复任务 |
| B3：区分缓存损坏与配置损坏 | `PrivateStore.Read()` 不处理解密/反序列化异常，`DataHub` 启动直接读天气/额度缓存；缓存写入异常也未与来源读取隔离 | 可重建缓存损坏时保留诊断并冷启动该模块；缓存写盘失败保留内存快照。配置或票据不可读时明确报错并保护原文件 | 损坏天气缓存不影响额度/硬件；缓存磁盘写入失败不退出桥接；配置损坏不被空默认值覆盖 |
| B4：远端结构变化可降级 | 部分解析使用 `GetProperty()`，后台只捕获部分异常类型 | 对必要字段做边界校验，在来源边界转换为模块失败状态，保留可用旧数据与简短脱敏错误码 | 缺字段、错误类型、异常数值均不停止其他模块；取消服务仍可及时结束 |
| B5：快照请求隔离旧响应 | `main.ts` 连接切换时 abort 后可开始新请求，旧请求的 finally 仍修改共享 `pending`；成功写入无请求身份校验 | 增加连接代次/请求身份校验，只有当前请求可提交数据或清理当前状态；暂停、恢复和换票据统一处理 | 延迟旧响应、换连接、快速暂停恢复时，无旧数据覆盖、无重复轮询任务 |

B1/B2 应保留额度来源优先级、绘图分类器的证据边界、已有超时和缓存上限。当前请求活动缓存已有 128 项上限，硬件历史已有 30 样本上限，液态光泽已有共享按需 RAF；这些现有控制应继续保留。

**B 的测试重点**：使用可控 HTTP 替身和临时私有目录验证超时、异常响应、取消、配置变更与写入失败。补真实故障分支的测试，不以增加测试数量作为完成标准。

## 5. C：优先减少前端重复计算

当前前端每秒唤醒轮询检查，正常约每两秒读取整份快照，随后调用天气、额度、硬件更新。现有实现已经复用大量 DOM 节点，文本也有相同值跳过写入；优化重点在模块调度和派生计算。

### C1. 按模块变化更新

- 为天气、额度、硬件使用独立修订标识或稳定内容签名，分别判断是否需要更新。签名应在来源实际变化时维护，避免每次轮询序列化整份快照。
- 未变化的天气不重复构建详情模型；未变化的额度不重复计算分页；硬件仅在新增样本或相关设置变化时更新曲线和统计。
- 本地过期判断、倒计时和自动翻页继续按到期时刻更新；数据没有变化也必须能从正常转为过期。
- 时间戳相同也可能发生 `ok → stale`、错误提示或显示设置变化，修订判断必须包含这些变化。

### C2. 减少计时器和格式化分配

- 用一个到期调度入口安排时钟、轮询、倒计时和刷新状态，保留独立网络超时控制；离线沿用退避，恢复及时读取。
- `ClockWeather.tick()` 当前每次创建多个 `Intl.DateTimeFormat`；按时区、12/24 小时和秒显示选项复用格式器。
- 缓存稳定 DOM 引用；浮层位置只在尺寸、位置、目标或内容尺寸变化时重算，减少 `CardDetails.sync()` 中重复布局读取。
- 保留现有按需 RAF、宿主 FPS 上限、减少动态、关闭动态和暂停取消机制。

**C 的验收条件**：

1. 硬件可见时保持默认两秒级采样展示，曲线仍基于真实样本；不会把重复快照算作新增采样。
2. 固定天气/额度测试数据、只更新硬件的 60 秒场景中，天气与额度的完整派生计算各只执行首次和必要的状态/设置更新；倒计时与过期提示继续正确。
3. 暂停后停止前端数据轮询和视觉调度，恢复后只启动一套任务；与上游自动刷新周期保持独立。
4. 翻页唯一性、两种额度过滤、零/未知、详情滚动位置与焦点、桌面输入保护均通过回归。
5. 在同条件资源对照中无显著回退；若收益落在噪声范围，优先保留易维护的实现，不宣称已降低资源占用。

## 6. D：测量后决定是否优化桥接采样

证据：`HardwareSampler` 目前持续每两秒采样，独立于前端是否暂停、组件是否显示；`/v1/client` 当前只保留最近一个客户端报告，不能直接用于判断所有消费者都已暂停。

若采样分析确认后台传感器更新占据主要可优化开销，再推进：

- 引入带过期时间的客户端需求记录，汇总所有 WE、浏览器与管理/探测消费者；不能让一个暂停窗口停掉另一窗口的数据。
- 硬件可见时维持两秒；全部消费者长期无需求时再降低采样频率，恢复时立即采样。具体闲置间隔在 A/B 后选择。
- 只在传感器选择/设备变化或需要查看清单时重建完整传感器清单；先测量，再决定是否缓存。
- 若支持硬件“省电档”，同步调整曲线的时间窗口裁剪和有效样本统计，避免改变采样间隔后仍把 30 点解释为一分钟。
- 上游额度刷新保持用户配置的十分钟节奏，天气保持既有刷新规则；前端暂停不应自动改变这些共享数据策略。

本阶段不预设 SSE/WebSocket、进程拆分或新框架。当前快照体量和桥接开销是否需要额外机制，应由测量决定。

**D 的验收条件**：单窗口、多个窗口、一窗暂停一窗活跃、全部暂停、浏览器关闭、需求记录过期与重新打开均行为正确；无消费者时采样工作确实减少，恢复后新数据及时到达。

## 7. 统一验证与资源预算

### 自动化入口

增加一个只验证、不安装的统一入口，串联现有前端检查、桥接检查以及有代表性的浏览器回归。浏览器用冻结时间、匿名快照与隔离桥接端口运行；现有依赖真实显卡型号、城市或会修改设置/触发真实刷新的脚本归入独立的本机验收步骤。

优先复用：`desktop_input_check.py`、`quota_pagination_check.py`、`image_quota_ignore_check.py`、`luna_ignore_check.py`、`liquid_glass_check.py`、`clean_layout_check.py`。进入统一入口前先明确每个脚本的数据依赖及副作用，避免把本机生产联调当作日常回归。

### 资源测量

1. 固定同一台机器、1600×2560、30 FPS、相同材质与账号数据；记录其他屏幕壁纸、前台程序、系统电源状态。
2. 建立当前版与候选版：预热至少 5 分钟，分别测量闲置和固定交互场景，每场景至少 10 分钟，交替重复至少 3 轮；另测暂停/恢复。
3. 分开记录 Web 的全部 CEF 进程、桥接、WE 主程序及 DWM；用相同的 CPU 归一化和 GPU 引擎计数口径。记录均值、中位数、P95、私有提交、私有工作集及显存。
4. 首个当前版基线确认后再锁定预算。建议初始回退警戒线：项目 CPU 均值增加超过 0.10 个百分点、Web GPU 3D 增加超过 0.30 个百分点、预热后私有提交中位数增加超过 10%。需超出重复测量波动且可复现，才能判定回退。
5. 候选版做 24 小时观察，涵盖断网恢复、睡眠唤醒、桥接重启、暂停恢复及反复开关详情；分析预热后的内存趋势与自然回落。短时上升或工作集合计上升都不能单独证明泄漏。

上述警戒线是建议验收预算，**不是已测结果或收益承诺**。采样顺序应保持可比，不能把其他屏幕或 DWM 的开销全部算到本项目。

### 正式桌面四类证据

| 证据 | 验收内容 |
| --- | --- |
| 资产一致 | 构建 ID、JS/CSS/HTML 摘要、属性迁移与配置保留 |
| 宿主数据健康 | 正式显示器选中目标、宿主上报版本、分辨率/FPS/暂停状态、数据连接 |
| 程序交互 | 生产包事件回放、release-only 输入、覆盖窗口/最小化保护、范围与分页、开合详情 |
| 真实桌面物理输入 | 实际点击账号、范围菜单、关闭、天气；覆盖窗口与最小化时不误触 |

程序回放通过与进程重建均不能替代最后一项。真实桌面验收结果单独记录。

## 8. 本轮建议安排

1. **第一批：A1+A2+A3。** 将正式安装与回退流程做成可靠入口，并取得当前资源基线。
2. **第二批：B1–B5。** 优先来源/账号隔离、缓存异常和请求代次，逐个故障分支验证。
3. **第三批：C1+C2。** 从格式器复用、模块变化判断开始，小步比较资源数据。
4. **评审点：** 若候选版已稳定且桥接开销很低，停止扩大优化范围；若证据指向后台采样，再实施 D。
5. **最终交付：** 更新脚本、回退记录、自动化检查入口、匿名资源对照报告、24 小时观察记录与正式桌面验收记录。

后续再评估新组件、统计图或发布能力。现阶段继续沿用轻量 TypeScript/CSS 和已确认的玻璃视觉、人物面部留白、CPAMP 时间范围与证据语义。
