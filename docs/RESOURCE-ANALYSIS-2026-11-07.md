# 资源与稳定性分析（第三步，2026-11-07）

本轮只做测量与分析：没有修改正式壁纸属性、桥接配置或运行中的程序。所有结论均标明证据范围；短时观察和非受控对比不作为“已降低占用”的依据。

## 0. 结论摘要

- **稳定性**：24 小时记录内健康接口与数据读取 0 失败、无长间隔；天气仅一次 29 分钟过期后自动恢复；5 次桥接重启均为计划内安装且无读取失败。额度聚合状态全程 `stale` 是聚合规则所致（今天确认由一个 10-19 后再无观测的绘图日窗口造成），前端显示不受影响。
- **内存**：没有泄漏证据。Web 私有提交在夜间闲置时走平、随交互缓慢上升，集中在 GPU 进程缓存；桥接 20 小时持平（CPU 0.058%）。10-23 记录的“私有工作集 +103 MiB”是新旧进程的驻留差异，私有提交几乎相同。
- **当前基线**：正式桌面 Web 合计 CPU 0.275%（中位 0.185%）、GPU 3D 中位 0.26%、私有工作集 83 MiB；桥接 CPU 0.065%。
- **受控 A/B**：前端在隔离 Chrome 中的持续开销约为 CPU 0.12%、GPU 3D 0.27%。玻璃模糊约占 GPU 时间的 30%（−0.080 个百分点），时钟秒与 2 秒硬件更新各约 −0.04~−0.06 个百分点；CPU 差异与占位场景同在噪声内。暂停时 CPU 0.004%、GPU 0。
- **决定**：各项都远低于路线图回退警戒线（CPU +0.10、GPU +0.30 个百分点），本轮**不为资源做前端代码改动**，也不推进桥接按需采样（D）。保留玻璃模糊与现有设置；用户可自行关闭“显示秒”。
- **修复**：`observe-stability.ps1` 截止前连发样本的缺陷；新增分析与 A/B 工具，`measure-resources.ps1` 可按 CEF 角色拆分。

### 1.2 额度聚合状态为何全程 `stale`

24 小时内快照的 `quota.status` 全部为 `stale`。桥接的规则是：任意一个账号的任意窗口观测时间超过 15 分钟（或上游标记 stale），聚合状态就是 `stale`（`RemoteSources.cs` 中 `accounts.SelectMany(a => a.Windows).Any(w => w.Stale)`）。观测脚本只记录了聚合值，无法回溯当时是哪个窗口。

2026-11-07 19:08 只读核对当前快照：11 个账号中只有一个 Codex team 账号的一个“日窗口 · 绘图（Premium）”过期——最后观测 10-19 23:35，重置时间 10-20 已过，CPAMP 快照仍返回这条记录。仅这一条就使聚合状态长期为 `stale`。前端 `currentQuotaWindows()` 已按单窗口过滤过期窗口，显示不受影响；但聚合状态因此**不能作为额度健康信号**。

后续可选（需确认后再改）：

- 观测脚本改为记录各窗口的过期数量与最久年龄，而不是只记聚合状态。
- 桥接对“重置时间已过一个完整周期且再无新观测”的窗口单独标记（或不计入聚合状态）。这涉及额度语义，不在本轮直接修改。

### 1.4 10-23 两个待解释数字的结论

10-23 记录的“Web 私有工作集 +103 MiB（101 → 205）”来自 10-22 22:30 与 22:46 两段 12 分钟观察：前者是已运行很久的旧实例，后者是刚安装重启的新实例；两者**私有提交中位数几乎相同（422.6 vs 424.1 MiB）**。私有工作集只是私有内存中仍驻留物理内存的部分，长时间运行的进程会被系统修剪，新进程则尚未修剪。因此这 +103 MiB 是驻留差异，不是多分配的内存。今天已运行约 9.5 小时的同一前端版本，私有工作集为 83 MiB（§2）。

“GPU 3D +0.18 个百分点（0.293 → 0.474%）”比较的是不同时间、不同桌面活动下的均值；中位数分别为 0.11/0.18/0.27%，今天正式桌面为 0.26%。它没有超过路线图建议的 +0.30 个百分点警戒线，且未受控；受控结果见 §3。

### 1.5 发现并修复的观测脚本缺陷

`observe-stability.ps1` 在截止前计算剩余等待时间时使用 `[math]::Min($IntervalSeconds, $remaining)`。PowerShell 会把 `(int, double)` 绑定到 `Min(Int32, Int32)`，剩余不足 1 秒时被截成 0，于是脚本在最后 0.4 秒内连发了 16 个样本（Windows PowerShell 5.1 与 PowerShell 7 均可复现：`[math]::Min([int]60, [double]0.39)` 返回 0）。已改为 `[math]::Min([double]$IntervalSeconds, $remaining)`；分析脚本也会剔除间隔小于 1 秒的样本。

## 3. 前端设置受控 A/B（隔离 Chrome）

### 3.1 方法

- 工具：`scripts/ab-frontend-resources.py`（进程采样 `scripts/sample-process-tree.ps1`）；结果目录 `artifacts/analysis/ab-frontend-20261107/`（`analysis.json`、`phases.json`、`samples.jsonl`、匿名 `fixture.json`）。时段 11-07 19:58–22:09。
- 前端：`dist` 构建 `20261107084128-210b5852`（提交 a46bb65，即下一次部署的源码，比正式桌面的 042c1ef0 新）。
- 浏览器：Chrome 156 无头模式，`chrome://gpu` 确认合成与光栅均为硬件加速；视口 1600×2560、DPR 1；独立进程树，不连接正式桥接（页面对正式桥接端口的请求一律拦截为 503）。
- 数据：开始时只读取一次正式快照并匿名化（11 个账号、32 个窗口），之后按生产节奏回放：硬件每 2 秒更新，额度与天气每 10 分钟更新，并提供与当前桥接相同的 `revisions`。
- 设置与正式桌面一致：流体模式、材质 83/26/68、显示秒、忽略基础模型周窗口与绘图额度、动态开启、30 FPS；通过 `wallpaperPropertyListener` 下发，与 WE 的方式相同。
- 排程：预热 5 分钟；3 轮，每轮 6 个场景，第 2 轮倒序、第 3 轮轮换起点；每个场景先稳定 1 分钟，再测 6 分钟（每 5 秒一个样本，共 72 个）。差值与同一轮的 A 配对。
- 指标：Chrome 进程树 CPU（按 16 个逻辑处理器归一化）、GPU 3D 引擎时间、专用显存；渲染进程主线程工作量来自 CDP Performance 指标。M（关闭动态）作为空闲占位：流体模式下环境光计时器本就关闭，流体高光只在指针交互时启动，闲置时理论上与 A 相同，用来估计噪声。

### 3.3 解读

- **CPU**：占位场景与 A 相差 −0.013 个百分点（A 第 1 轮紧接预热、偏高），S/C/H 的差值 −0.013~−0.021 与之同量级，不能认定任何设置改变了 CPU。前端合计约 0.1 个百分点。
- **GPU**：占位场景 +0.006，可视为噪声上限。模糊为 0 三轮都在 0.18–0.19%，比 A 低 0.080 个百分点，约占前端 GPU 时间的 30%；冻结硬件更新三轮一致地低 0.044；不显示秒低 0.057（第 3 轮差异较大）。差异可重复，但绝对值很小。
- **每秒更新**：活动时约 91 次布局/分钟。冻结硬件后降到 70，说明 2 秒一次的硬件更新约贡献 21 次；其余约 70 次/分钟主要来自每秒一次的计时更新：额度倒计时按 `HH:MM:SS` 显示，每秒都有文字变化，所以关闭“显示秒”并不减少布局次数，只减少时钟所在玻璃区域的重绘。倒计时改为分钟精度可能再省一部分 GPU 时间，上限是冻结硬件且不显示秒后仍剩余的约 0.17 个百分点，实际会更少，且会改变显示方式；未实测，不建议为此改动。
- **暂停**：CPU 0.004%、GPU 0、主线程 0.4 ms/分钟；专用显存降低约 22 MiB，GPU 进程私有提交降低约 29 MiB。暂停路径工作正常。
- **与正式桌面对照**：正式桌面 Web 的 CPU（24 小时记录 0.18–0.29%）和 GPU 3D 中位（0.26%）与隔离 Chrome 同一量级；WE 的 CEF 与 Chrome 版本、离屏帧率不同，因此只用这里的相对差，不用绝对值替代正式桌面数据。

### 3.4 Chrome 无头环境的内存假象（已排除前端泄漏）

A/B 中渲染进程私有提交在活动时线性增长约 0.8 MiB/分钟，暂停时增长为 0；JS 堆保持 2.5–3.4 MiB，事件监听器恒为 83 个，DOM 节点在 690–1100 间波动而无单调增长。为判断来源，另用不附加任何 DevTools 会话的普通无头 Chrome、同一回放数据各运行 15 分钟：

| 前端 | 渲染进程私有提交增长 | 快照请求 |
| --- | --- | --- |
| 正式桌面版 042c1ef0（直接读取 WE 项目目录） | 0.583 MiB/分钟 | 385 次 / 16.1 分钟 |
| 当前源码 210b5852 | 0.582 MiB/分钟 | 386 次 / 16.1 分钟 |

两个版本增长率相同（约每次快照轮询 25 KB），而同一 042c1ef0 在 WE 的 CEF 中运行 9.5 小时后渲染进程私有提交仍只有 58.6 MiB，24 小时记录中对应进程也基本持平。因此这是 Chrome 156 无头环境特有的现象（具体原因未定位），不是 10-23 之后引入的前端回退。A/B 的内存数值（私有工作集也在 2 小时内随修剪从约 225 降到约 120 MiB）不用于结论；CPU/GPU 的配对差不受影响。若 WE 以后升级 CEF，应复查渲染进程私有提交趋势。

### 3.5 局限

- 只测了闲置场景；悬停高光、打开详情、翻页等固定交互未测。
- 回放数据除时间戳和硬件读数外保持不变，没有覆盖额度刷新失败、账号增减等状态变化。
- 每个场景测 6 分钟（路线图建议 10 分钟）；因三轮结果一致且有占位场景估计噪声，用于诊断足够，但不作为候选版验收数据。

## 4. 决定与后续

1. 本轮不做资源导向的前端或桥接代码改动：前端合计约 0.1% CPU、0.27% GPU 3D，桥接约 0.06% CPU，均远低于路线图回退警戒线；按路线图“收益落在噪声范围时保留易维护实现”的原则停止扩大优化范围。D 阶段（桥接按需采样）继续搁置。
2. 玻璃模糊是主要 GPU 成本但属于核心视觉，保留。“显示秒”已是属性开关，是否关闭由用户决定（约省 0.05 个百分点 GPU）。
3. 下次部署后，用修复后的 `observe-stability.ps1` 做一次新版本 24 小时观察，重点看 GPU 进程私有提交在多日内是否走平；同时考虑让观察脚本记录各窗口过期数与最久年龄（见 §1.2）。
4. 额度聚合状态与长期失效窗口的处理（§1.2）涉及额度语义，另行确认后再改。
5. 资源结论已稳定，可转入第四步（设置页体验：统一账号列表、未保存提示、诊断折叠）。
